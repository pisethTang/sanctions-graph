================================================================================
1. WHAT THIS PROJECT IS
================================================================================

SanctionsGraph screens education agents / international applicants against global
sanctions and PEP lists (OpenSanctions data), then visualizes the *why* behind a
hit — shared addresses, identifiers, and 2nd-degree network links — as an
interactive graph.

The domain premise: 90-95% of screening alerts are false positives. So the
product value is *auditable explanations*, not just a match score. Every model
and every match tier exists to preserve traceability back to the source record.

This is an early-stage learning project. Owner is building it to learn Django +
Vue properly, so explanations of *why* matter as much as working code.

3. DATA MODEL (backend/screening/models.py) — 7 models
================================================================================

Agent                 The subject being screened. Fields: name, aliases (JSON
                      list), addresses (JSON list), birth_date, nationality (2-char).
SanctionedEntity      A person/org from OpenSanctions. `source_id` is the
                      OpenSanctions ID and is UNIQUE — ingestion must upsert on it.
                      `entity_type` is 'person' | 'organization'.
EntityAlias           Name variations. Fuzzy-match surface (pg_trgm).
EntityAddress         `full_text` is the fuzzy-match surface (pg_trgm).
EntityIdentifier      Exact-match only. Stored as SHA-256 of the stripped,
                      upper-cased value via EntityIdentifier.hash_value().
                      *** NEVER store a raw passport or tax number. ***
ScreeningCase         One screening run. `network_snapshot` (JSON) freezes the
                      graph as it was at run time, so an old decision stays
                      auditable after the sanctions data refreshes.
Match                 One hit: match_type, confidence, human-readable
                      `explanation`, plus resolved/resolution for the officer's
                      false-positive verdict.

match_type choices are the RANKED EVIDENCE TIERS. Map new matching logic onto
them rather than inventing parallel scoring:
  identifier_exact > name_exact > name_fuzzy > address_fuzzy > network_2nd_degree

4. WHAT IS BUILT AND WORKING

--- Ingestion -----------------------------------------------------------------
backend/screening/management/commands/ingest_opensanctions.py

Streams the FollowTheMoney JSON-lines dump line by line (the file is ~2.6 GB —
NEVER json.load() it, never `git add` it; it is untracked AND not in .gitignore).

Source: https://data.opensanctions.org/datasets/latest/default/entities.ftm.json
Downloaded to backend/data/entities.ftm.json

FtM envelope: every record has id, caption, schema, properties, datasets, target.
The keys inside `properties` differ by schema, and EVERY VALUE IS A LIST even
when there is one item.

Field mapping:
  id                          -> SanctionedEntity.source_id
  schema (Person/Company/...) -> SanctionedEntity.entity_type
  properties.name[0]          -> SanctionedEntity.name
  properties.alias[]          -> EntityAlias
  properties.address[]        -> EntityAddress
  passportNumber, taxNumber, idNumber, registrationNumber, innCode, ogrnCode,
  leiCode                     -> EntityIdentifier (HASHED)

`alias` and `address` are frequently ABSENT on Person records — handle missing
keys, don't assume the Company shape. `target: true` means the entity itself is
sanctioned/wanted.

Flags: --limit N. Batches of 1,000 with bulk_create(ignore_conflicts=True).

*** CRITICAL GOTCHA baked into this command ***
bulk_create(ignore_conflicts=True) does NOT populate primary keys. So the code
pre-queries existing source_ids (for re-run safety), bulk_creates, then RE-QUERIES
to build a source_id -> pk id_map before creating the FK children.

STATUS: written and reviewed, but the live ingest against the full file has NOT
been run yet. That is still the untested half.

--- Matcher -------------------------------------------------------------------
backend/screening/matcher.py — ScreenMatcher, 5-step pipeline. 13/13 tests pass
(backend/screening/test_matcher.py).

Tiers and confidences:
  identifier_exact     100
  name_exact            95
  name_fuzzy            similarity score * 100
  address_fuzzy         similarity score * 100
  network_2nd_degree    50

Thresholds — DELIBERATELY LOWER than first specified, measured against real data:
  NAME_FUZZY_THRESHOLD    = 0.6   (0.7 was too high: similarity('Vladimir Putin',
                                   'Vladimir Putni') = 0.667)
  ADDRESS_FUZZY_THRESHOLD = 0.4   (0.6 was too high: similarity('Moscow, Russia',
                                   'Moscow, Russian Federation') = 0.481)

Dedup is by TIER PRECEDENCE first, then confidence — NOT by raw confidence.
Reason: an identical name scores similarity 1.0 -> name_fuzzy@100, which would
wrongly beat name_exact@95.

  if (new_rank, -match["confidence"]) < (current_rank, -current["confidence"]):

Fuzzy name SQL unions BOTH EntityAlias.text AND SanctionedEntity.name.
Network tier uses NetworkX single_source_shortest_path_length(cutoff=2).

*** HARD SECURITY CONSTRAINT: all SQL must be parameterized. No f-strings, no
    string formatting in queries. ***

pg_trgm is required. It is enabled via TrigramExtension() inside migration
0003_agent_addresses_trigram.py so the test DB gets it too.

--- API -----------------------------------------------------------------------
backend/screening/serializers.py, views.py, sanctionsgraph/urls.py
5/5 tests pass (backend/screening/test_api.py). No authentication anywhere.

  POST /api/agents/            create an Agent
  POST /api/screen/            run the matcher, persist ScreeningCase + Matches
  GET  /api/cases/            list
  GET  /api/cases/{id}/       detail (agent + all matches + network_snapshot)
  GET  /api/cases/{id}/network/   Cytoscape-format graph

Cytoscape format: {nodes: [{data:{id,label,type,risk_score}}],
                   edges: [{data:{source,target,label}}]}
Node ids are namespaced "agent-{pk}" / "entity-{pk}" so an agent pk can never
collide with an entity pk.
case.risk_score = max confidence across matches (default 0).
network_snapshot is written at screen time; the /network/ endpoint prefers the
snapshot and only rebuilds live if it's empty.
build_network() also emits entity<->entity edges for shared_address and
shared_identifier — those are the "why" links.

KNOWN OPEN DESIGN QUESTION: POST /api/agents/ accepts an `identifiers` field and
SILENTLY DISCARDS it (identifiers only ever exist hashed, at screen time). It may
be better to 400 instead. Not decided.

The tests were written FIRST (TDD) and mount components BARE — no router plugin,
no fetch mock. That forced three non-obvious decisions; do not "clean these up"
without re-running the tests:

  1. .results / .match-list / .graph-container render UNCONDITIONALLY.
     AgentForm sets `submitted.value = true` BEFORE any await so the panel is in
     the DOM after a single tick. All fetch calls are try/caught — otherwise the
     rejected fetch surfaces as an unhandled rejection.

  2. CaseDetail reads the route off getCurrentInstance()?.proxy.$route, NOT
     useRoute(). The test passes global.mocks.$route (options-API style);
     useRoute() is inject()-based and would be undefined there. vue-router
     registers $route as a global property so this also works in the real app.

  3. CaseList uses <a @click.prevent> with an optional-chained router?.push(),
     not <RouterLink>. Without the plugin RouterLink throws; this keeps the test
     deterministic even if the backend happens to be running.

  4. vite.config.ts imports defineConfig from 'vitest/config' and sets
     test.environment = 'jsdom'. Without this vitest defaults to node, where
     `document` doesn't exist and mount() cannot work.

Cytoscape init is wrapped in try/catch — jsdom gives it no layout box to measure.

5. CURRENT FOCUS — DATA PROFILING
================================================================================

backend/profile.ipynb — profiling the raw FtM dump to find patterns worth
visualizing. Sample size 100,000 lines. Findings so far:

Schema distribution (of 100k lines):
  Occupancy    53.1%   <- NOT entities; these are PEP position records
  Person       21.7%
  Company      10.8%
  Succession    4.9%
  Vessel        2.0%
  LegalEntity   1.8%
  Organization  1.7%
  Family        1.2%   <- relationship edges
  Ownership     1.0%   <- relationship edges
  UnknownLink   0.7%
  Address       0.4%
  Directorship  0.2%

  => Only ~36% of lines are the four schemas the ingest command keeps
     (Person/Organization/LegalEntity/Company). The majority are Occupancy
     records and relationship/interval schemas.

target flag:  34,310 True (sanctioned/PEP)  vs  65,690 False (related parties)

Top countries: us 18143, ru 3250, cn 1473, tr 467, ir 443, mx 339, hk 336,
               ae 335, gb 243, in 234, ua 164, de 159

Field presence (the match surfaces):
  Has address:     26.7%
  Has alias:        9.2%    <- sparse; fuzzy name matching leans on entity.name
  Has identifier:  19.3%

Interesting counts within the sample:
  Entities with 2+ addresses: 18,949
  Persons with 2+ aliases:     1,237
  Orgs with registration numbers: 3,265

Qualitative observations from the samples:
  - Multi-address entities are usually THE SAME address transliterated into
    several languages/scripts (Ukrainian, Russian Cyrillic, English). e.g.
    "Elektrostal ChemicalMechanical Plant" has 4 addresses that are all
    Karl Marx St. 1, Elektrostal. This is exactly the case address_fuzzy at 0.4
    is tuned for, and it argues for normalizing/transliterating before matching.
  - Aliases are heavily cross-script too (Japanese, Cyrillic, Latin for the same
    person). Trigram similarity will NOT bridge scripts — that is a real gap.
  - One alias in the data is literally the string "Input Name" — the source data
    has junk in it.

NEXT STEP: find shared-address clusters (the notebook's last cell builds
address_to_entities and sorts by cluster size). These clusters are the strongest
candidate for a compelling graph visualization, since a shared address linking
several sanctioned entities is precisely the "why" the product is meant to show.

6. WORKING CONVENTIONS — FOLLOW THESE
================================================================================

* TDD, STRICTLY. Write the comprehensive test suite BEFORE implementing any
  feature. Do not edit existing .test.ts / test_*.py files to make things pass.

* BRANCH FIRST. Create the feature branch off up-to-date main BEFORE writing any
  code, not after. Name it after the feature: feat/<name>, fix/<name>.
  Work happens on feat/* branches; main is the PR target.

* Git: do NOT squash, do NOT delete the branch.
    gh pr merge --merge          <- merge commit, branch kept
  Only GENERATE the git/gh commands as a block for the owner to run. Don't run
  them unprompted.

* Commit prefixes: `feat:` for code, `A:` for logbook/README additions.

* After a substantive session, append to today's .logbook/DD-Month-YYYY.md —
  including the failures and the reasoning, which is the whole point of the
  journal. Write it in the owner's voice: first person, plain, no em-dashes,
  not robotic. Do not modify existing logbook content, only append.

* Do not run commands (especially migrate) that weren't asked for. The owner

  without permission.

* Verify remote/PR state IN THE SAME TURN as making a claim about it. A stale
  `gh pr` check from earlier in the conversation caused wrong advice once.

* Explain the WHY, concisely. The owner is learning and asks "why does this step
  exist" — answer that directly, don't just hand over code. But keep it SHORT;

7. GOTCHAS / TRAPS
================================================================================

- Postgres container must be running or `runserver` fails with "Connection
  refused" — runserver always hits the DB because check_migrations() sits
  OUTSIDE the skip_checks guard. Fix: docker start sg-postgres
  Consider: docker update --restart unless-stopped sg-postgres  (not done yet)

- "password authentication failed for user sguser" is a DIFFERENT problem: a
  native postgresql service is bound to 5432 and answering instead of the
  container. Check `sudo lsof -i :5432`, stop the native service.

- pytest needs pytest.ini with DJANGO_SETTINGS_MODULE; DB tests need the `db`
  fixture or they raise "Database access not allowed".

- settings.py calls bare load_dotenv(), which looks for a file named exactly
  `.env` from the cwd upward. The actual env files are backend/.env.backend,
  backend/screening/.env, frontend/.env — so NONE of them is found and settings
  fall through to the hardcoded defaults (sguser/sgpass/localhost:5432).
  This is true for both `uv run` and F5. NOT fixed — it's a real behavior change
  to how secrets load, left for the owner to decide.

- settings.py still has DEBUG=True and a generated SECRET_KEY fallback.

- README.md describes GitHub Actions CI/CD and Vercel/Railway deploys as if they
  exist. They do not. No .github/ workflows are present.

- frontend/src/views/Home.view.vue is now orphaned (router points at AgentForm).

- The production bundle is ~529 kB because of cytoscape. Warning, not an error.
